## The footer rule — this cost 13 episodes tonight, read it

**LeRobot commits the parquet footer when the recording run ends, not per
episode.** Every `✓ SAVED episode N` you see is not yet durable. If the run dies
uncleanly, the data parquet has no footer and the *entire dataset* is
unreadable — not just the last episode.

Confirmed by the datasets themselves:

```
medbottle_pick_CRASHED_NO_FOOTER    2 ep   BROKEN     (named for it)
glassbottle_pick_v2                13 ep   BROKEN     (tonight)
bottle_pickplace_OLD_BROKEN_BOTTLE 12 ep   OK
medbottle_pick_RETIRED_GRIP45       3 ep   OK
medbottle_pick_DEFORMS_GRIP60       2 ep   OK
glassbottle_pick                   20 ep   OK
```

Every dataset from a run that finished has `PAR1`. Both that died mid-run do not.

**Ctrl-C is clean.** Verified directly: a batch interrupted with Ctrl-C
finalised with a valid footer and 4 episodes intact. `KeyboardInterrupt` lets
the cleanup path run. What destroys a dataset is an *unclean* stop where no code
executes — a kernel hang or a power cut.

**So: record in batches of 5.** A hang then costs one batch.

```bash
# batch 1 — creates
... record_kinesthetic.py --repo-id local/NAME --episodes 5 ...
# batches 2,3,4 — note --episodes is the RUNNING TOTAL, not the increment
... --episodes 10 --resume ...
... --episodes 15 --resume ...
... --episodes 20 --resume ...
```

`--episodes 5 --resume` against 5 existing episodes exits immediately without
recording: `kept = dataset.meta.total_episodes` and the loop is
`while kept < args.episodes` (`record_kinesthetic.py:423`). It is a no-op, not
an error, and it looks like a crash if you are not expecting it.

**`--resume` writes a new file, not a rewrite.** Batch N lands in
`data/chunk-000/file-00N.parquet`. Committed batches are therefore immutable —
a later crash cannot corrupt them. This is better than it needed to be.

Check any dataset in seconds:

```bash
tail -c 4 <dataset>/data/chunk-000/file-000.parquet | xxd -p   # must be 50415231
```

# Addendum, 31 August ~03:30 — the policy does not move, and why

Training finished cleanly (2 h 49 m, loss 7.725 -> 0.085, checkpoints archived and
md5-verified). The smoke test failed in three stages, and the third one is the
real finding.

## 1. Deployment never replayed the start pose

`act_policy_control.py` has no start-pose handling: it infers from wherever the
arm happens to be. Every training episode began from `record_start_pose.json`
replayed to within 0.3 units, so the first smoke test started **1887 raw counts**
out of distribution on `shoulder_lift` and lurched.

A related trap: **the arm does not fall back to the rest pose.** The STS3215
gearing holds position with torque disabled — measured 1886 counts away with
torque off the whole time. "Rest pose" is where the arm is *put*, not where it
falls. `scripts/goto_start_pose.py` (new) replays it: measured 12 counts residual
over 1887 counts of travel.

## 2. The twitching is a control-loop artefact, not a policy fault

24.28 Hz realised against a 30 Hz target. Every `n_action_steps` the loop stalls
~100 ms for inference while the servo holds its last goal, then receives a large
delta — a ~2.4 Hz judder. `--smooth A` was added to
`act_policy_control.py` (exponential smoothing on commanded joints, gripper
unfiltered, default 1.0 = unchanged so no prior measurement is affected).
Untested against a working policy.

## 3. CORRECTED — the policy self-locks on an attractor built from idle frames

An earlier version of this addendum blamed a joint limit. **That was wrong** and
is retained only as a warning against the reasoning: `range_min` is where the
calibration sweep stopped, not a mechanical stop, and the commanded -105.66
normalised maps to raw ~602, which the servo can reach. The arm was in range.
Resting was not the problem.

### What the probe actually showed

From the start pose, six consecutive inferences with nothing sent to the motors:

```
cmd0 -105.66   cmd1 -105.74   cmd2 -105.80   cmd3 -105.72   cmd4 -105.80   cmd5 -105.85
```

0.19 units of variation. The policy is at a **fixed point**: it commands a pose
~5 units from where the arm is, executing it changes the state too little to
matter, the next observation is identical, and the same command comes back. The
arm consumes a fraction of a unit of slack and stops. That is exactly the
observed "moved for a second and just stopped".

### Why — and it is caused by the fix we made on purpose

Every take begins with the operator holding still before starting to move.
Measured across both datasets:

```
                        start dead time        start-pose spread
old glassbottle_pick    9.7%   median 1.47 s        18.5
new v3                 10.8%   median 1.43 s         0.3
```

**The dead time is the same. What changed is where it lands in state space.**

In the old dataset the start pose varied by 18.5 units, so ~1000 "hold still"
frames were spread over 20 distinct poses and no single state carried a strong
do-nothing label. That policy moved (badly, but it moved).

In `v3` the start pose is reproducible to 0.3 units, so **all** of that dead time
piles onto one point: about 10% of the whole dataset teaches "when you see
exactly this observation, stay where you are". ACT is Markovian on (image, state)
with no clock, so at deployment it cannot know it has already been still for
thirty seconds. It sits in the strongest mode it was taught.

Pinning the start pose was necessary to force visual conditioning. It also
concentrated every idle frame onto a single state. Both are true.

### The fix — the 20 episodes are probably salvageable

**Trim the leading stationary frames from each episode.** ~930 of 8621 frames,
leaving ~7700. That removes the attractor and keeps the fixed start pose, which
is the property the whole re-recording existed to obtain. No re-recording.

Threshold used for the measurement above: first frame where any body joint has
moved more than 1.0 normalised unit from frame 0. Median 43 frames, max 74.

If rebuilding the dataset (parquet + re-encoded video + episode index) proves
more trouble than it is worth, the alternative is to re-record while **starting
to move the instant ENTER is pressed** — the dead time is an artefact of the
operator, not the protocol.

Either path still needs `--policy.chunk_size=50` on the retrain (see below).
